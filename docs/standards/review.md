# Review 规则

适用于代码、测试、工具、配置及规范文档的变更审查。审查前读取[代码规范](code.md)，再按影响范围读取[前端](frontend.md)和[后端](backend.md)规则；实际产品合同查[插件指引](../../browser-extension/AGENTS.md)。

## 从第一性原理出发

Review 的产出是有依据的风险判断：变更是否解决了要求的问题，是否破坏既有行为，今后的修改是否仍可理解和验证。测试通过提供有限证据，代码简短或符合个人偏好也不能证明正确。审查既要阻止确定的回归，也要允许有证据的改进交付，不能要求无关的完美重构。事实与个人偏好的区分参考 [Google 工程审查准则](https://google.github.io/eng-practices/review/reviewer/standard.html)。

## R1 固定审查对象和验收问题

- 记录需求来源、目标行为、变更范围和受审版本。PR 使用 base/head 及实际受审 SHA；本地改动记录基准、涉及文件和未提交差异，不能把旧提交的结论套到新工作区。
- 先读 diff，再沿实际调用链查看必要上下文：调用方、状态所有者、持久化与外部边界、兼容分支及测试。只读新增代码不足以判断副作用，整仓漫游也不能替代聚焦风险。
- 区分本次引入、被本次触及或放大的问题与无关旧问题。结论覆盖实际审查范围，不推断未查看模块已经安全。
- 用户授权、发布与仓库保护属于操作边界，审查通过不自动授权修改、合并、推送或发布；实际步骤按[贡献指南](../../Contribution.md#github-同步)执行。

## R2 同时检查需求与工程质量

| 维度 | 必须回答的问题 |
| --- | --- |
| 需求 | 正常、失败和取消时的行为是否符合验收？是否遗漏入口或改变用户已确认的语义？ |
| 状态与数据 | 哪份数据是事实来源？提交快照、当前输入和历史是否隔离？旧响应、重复请求与跨窗口写入如何处理？ |
| 边界与安全 | 输入在哪验证？来源与权限在哪检查？外部数据能否越权影响路径、命令、凭据或请求目标？ |
| 结构与维护 | 业务规则是否落在正确模块？是否复制规则、引入无实际收益的抽象或隐含依赖？ |
| 兼容与恢复 | 旧数据、旧页面、服务重启和部分成功如何恢复？失败后是否保留原件和可恢复结果？ |
| 验证 | 测试能否在真实错误发生时失败？来源是否与受审版本一致？报告哪些场景没有覆盖？ |

只列适用项的证据和问题，不复制整张检查表作为每次审查的交付物。文档变更重点检查指令是否可执行、路径是否有效、规则是否矛盾、是否把建议写成已实现事实。

## R3 先审会造成实际损失的路径

本仓库以下路径必须按改动影响检查，并使用对应开发规则判定：

1. **输入与历史隔离：**逆向、生图、自动衔接和批次使用各自受理快照；后续表单、图序、语言、模型或配置变化不串改在途任务。历史回放读取当次版本的输入。
2. **异步与取消：**切换项目、模式、版本或卸载后，迟到响应不覆盖新界面或夺焦；已受理任务按原快照后台继续属于预期。取消失败、交接空隙和重复回包不能误启动后续阶段或提前释放占用。
3. **数据与恢复：**保存失败不发布假成功；迁移、清理和重启不丢原数据、未提交引用或可恢复输出。重试保存不重新调用模型，隐藏不等于删除。
4. **权限与隐私：**消息来源、HTTP 鉴权、路径与下载目标分别检查；凭据不得泄漏到 content script 或宿主页面，完整私有会话正文不回传扩展。用户图片仅按已授权功能展示或传输；真实凭据、用户图片和私有会话不得进入公共日志、测试夹具或发布包。
5. **用户操作：**共享组件覆盖工作台和轻量端；关键操作在窄屏、键盘和失败状态仍可完成。自动检查不能替代未覆盖的焦点、视觉或真实扩展验证。

## R4 每条问题都必须有可行动证据

- 问题说明包含触发条件、精确位置、实际与预期差异、用户或系统影响；必要时给最小复现、失败测试或足够完整的静态调用链。没有运行过就标注“静态推导”。
- 优先定位能修复根因的最小行段，说明修复应保持什么合同；无须为每条问题预写整套实现。
- 对尚无证据的猜测标记待核实问题，不包装成已确认缺陷。无法验证时说明缺少的环境或输入，以及它如何限制结论。
- 同一根因合并为一条问题，列出受影响入口；不同根因分开。避免把纯命名或个人偏好写成阻断项。

### 严重程度与处理

| 等级 | 判定 | 处理 |
| --- | --- | --- |
| P0 | 无需特殊前提即可造成广泛不可用、严重数据破坏或安全事件 | 立即阻断交付，优先修复 |
| P1 | 在受支持、实际可达路径上造成重大功能失效、数据损失、越权或重复付费操作 | 修复后重新审查 |
| P2 | 有明确条件和影响的功能错误、兼容性回归或关键合同违背 | 原则上修复；延期须明确记录影响、缓解措施及维护决策，不能隐去风险后写“通过” |
| P3 / 建议 | 不影响当前正确性的可读性、维护或可选体验改进 | 明确标注非阻断，不用建议数量衡量审查质量 |

严重程度按发生条件和后果确定，不按改动行数或措辞强弱确定。确认的数据损坏、权限绕过及关键恢复缺口不能作为风格建议放行。

## R5 验证证据必须匹配结论

- 检查实际命令、退出状态、受检来源、适用环境、跳过项和报告限制。构建、类型检查、单元测试、合成预览、隔离扩展、真实用户环境和模型实测分别说明，不能相互冒充。
- 优先运行能区分错误与正确实现的检查，包括必要故障反例。测试数量增加、代码覆盖率或截图“看起来正常”不能单独证明关键行为。
- 复用证据前核对来源与有效性；文件、构建产物、fixture、检查器或环境变化后，重新判断哪些结论仍成立。具体条件按[实现与验证流程](../../Contribution.md#实现与验证)和[工具索引](../../agent-tool/README.md#开发反馈最终证据与耗时)，不另创一套标准。
- 未运行的测试、失败和未解决问题必须披露；不得声称“全部通过”后把例外埋在附注里。验证范围不足时给出“待验证”，不要以“未发现问题”代替通过。

## R6 给出明确结论并复核修复

审查输出保持简短，依次写：受审范围与版本、按严重程度排序的问题、实际验证与限制、结论。无发现时明确写“在上述范围内未发现可确认问题”，同时保留必要的验证限制。

结论使用以下含义：**通过**表示适用规则和必要证据满足、没有未解决的阻断问题；**需修改**表示存在已确认问题；**待验证**表示缺少影响判断的必要证据。产品取舍未明确时记录待决定事项，不替用户定义需求。

修复后核对新差异、原复现是否消失、相邻入口是否回归及版本是否漂移，再更新原问题状态。回复“已修复”或补充一项通过测试都不自动等于问题关闭；合并条件与发布检查仍以[贡献指南](../../Contribution.md)为准。
