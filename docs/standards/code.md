# 代码规范

适用于生产代码、测试和开发工具。前端与后端在此基础上分别遵循[前端开发规则](frontend.md)和[后端开发规则](backend.md)；[review 规则](review.md)规定如何核验。

## 从第一性原理出发

软件的价值是持续、可靠地满足需求。修改成本主要来自需要同时理解的状态、依赖和隐含约定；错误风险主要来自边界输入、状态变化与副作用。代码应让这些内容在局部可见，并使关键行为可以验证。精简指减少理解负担，不以字符数、文件数或抽象层数衡量质量。

以下是新增及本轮修改代码的标准，不代表存量代码已全部符合。发现存量问题时判断其是否影响本次正确性，再确定修复范围；不借规范建设做无关的全仓重写。规则中的“必须”“不得”是约束，“优先”允许有证据的取舍。

## C1 先定义可观察行为，再选择实现

- 实现前明确输入、输出、状态转换、失败行为和必须保持的不变量。功能修复要能说明哪个条件下出现了什么错误，以及修复后如何观察到差异。
- 范围以需求为界，复用现有术语和业务语义。项目、任务、提示词版本、图片资产等词义查 [GLOSSARY.md](../../GLOSSARY.md)，不要为同一概念另造名称。
- 兼容性是合同的一部分：区分新输入、旧记录和在途任务。协议或存储语义变化必须明确旧值如何解释、失败如何恢复；不能用新默认值静默改写旧意图。

## C2 让规则有明确归属

- 一个业务决策由一个模块维护，通过有意义的接口供调用者使用。界面、HTTP 路由和预览可以适配环境，但不能各复制一套资格判断、状态转换或尺寸规则。
- 边界适配负责解析、鉴权和装配；业务模块负责规则；I/O 模块负责实际资源操作。按职责分离即可，不为每次调用机械增加 controller/service/repository 层。
- 仅在封装真实复杂度、隔离副作用、复用同一规则或提供必要测试替换点时增加抽象。单纯改名转发、预想的扩展点和只有一个空壳实现的框架不能作为拆分理由。
- 一段直接代码能清楚完成工作时直接写。提取函数应给概念命名或隐藏完整细节；不要让读者为理解一项操作在多个无实质逻辑的函数间跳转。
- 将会一起变化的规则放在一起。模块入口和既有边界见[架构说明](../../browser-extension/docs/architecture.md)，开发工具归属见[贡献指南](../../Contribution.md#agent-工具的工程边界)。

## C3 数据结构表达有效状态

- 每份可变状态有明确所有者；能从现有状态可靠推导的值不再保存第二份。缓存必须有来源、失效条件和可接受的陈旧范围。
- 用稳定身份关联对象，不用可变标题、列表下标或当前选中项替代项目、任务和资产 ID。允许改序的列表必须保留对象身份。
- 区分缺失、显式清空、零、失败和加载中；不能用 truthy/falsy 合并业务上不同的状态。数字字段明确单位、有限性、上下界及舍入规则。
- TypeScript 边界输入先视为未验证数据，通过运行时检查收窄；类型断言不构成校验。优先用可判别联合表达互斥状态，不用多个可矛盾的布尔值拼状态机。收窄机制见 [TypeScript 官方说明](https://www.typescriptlang.org/docs/handbook/2/narrowing.html)。
- 避免用 `any`、非空断言、宽泛可选字段或关闭检查器掩盖未知状态。确有外部类型缺口时，把例外限制在适配边界并解释可验证的前提；不为此改写整个模块。

## C4 副作用必须有生命周期

- 发起异步操作时确定它属于哪个上下文、使用哪份输入、何时失效，以及谁负责清理。不能在执行中重新读取已变化的全局选择替代提交输入。
- Promise 必须被等待、返回，或进入有错误和清理处理的后台执行入口。`await` 用于有依赖的步骤；独立工作可以并发，但必须处理全部结果和并发上限。
- 定时器、监听器、端口、子进程、临时文件与对象 URL 都要明确释放路径，包括失败、取消和卸载。`finally` 的清理错误不能覆盖原始业务错误。
- 简单流程优先使用 `async/await`；串行队列等有清晰语义的 Promise 链可以保留。不要为了统一写法破坏既有调度或取消语义。

## C5 错误必须保留真实状态

- 边界校验失败、状态冲突、依赖不可用、用户取消和内部异常应可区分。沿用现有错误合同，不引入与调用方不兼容的第二套错误框架。
- 失败不得伪装为空列表、成功、默认模型或已保存。返回足够定位问题的信息，并向用户说明可执行的恢复动作；敏感内容不得进入错误响应或日志。
- 只在可以恢复、补充上下文或完成必要清理的层捕获错误；不能空 catch 吞掉主操作失败。确属尽力清理或可选能力时，写清忽略的原因及其不影响主结果的前提。
- 日志记录阶段、关联 ID、错误类别和耗时；避免重复逐层打印同一错误，不输出凭据、完整私有会话、图片字节或未经必要裁剪的外部响应。

## C6 表达保持直接、稳定

- 名称表达领域含义和单位；函数名表达动作，布尔名表达可判定条件。注释说明原因、不变量或外部限制，不逐句翻译代码。
- 在触及文件内沿用现有格式和导入约定；新建 JS/TS 文件默认使用 ESM、两空格缩进、双引号与分号。文件命名跟随同目录惯例，React 组件使用 PascalCase。
- 优先 `const`、显式依赖和早返回。避免深层嵌套、嵌套三元表达式、隐式修改传入对象和与职责无关的共享可变变量。
- 不把格式化、批量重命名、依赖升级或未触及模块整理捆绑进功能修复。删除因本次变更失效的分支、注释和测试，不保留会误导后续修改的死代码。

## C7 验证行为和失败边界

- 测试通过真实模块接口断言可观察结果；在网络、进程、时钟、随机数或文件系统边界替换依赖，不复制生产算法生成“预期值”。
- 新增行为和关键修复优先覆盖正常路径与会破坏不变量的失败路径。按需覆盖乱序、重复请求、取消、保存失败、恢复和旧数据；不为每个简单表达式增加镜像测试。
- 测试标题说明条件、操作与结果；产品行为场景按[实现与验证流程](../../Contribution.md#实现与验证)组织。技术检查如实说明范围，不冒充用户行为或实机验收。
- 断言来自需求及已确认设计。不能为让当前实现通过而减少必要断言、接受错误基线、扩大超时或隐藏跳过；修正错误测试须说明其原假设为何不成立。

## C8 用证据决定额外复杂度

- 添加依赖前检查现有模块、平台能力和实际需求，说明新增依赖解决的问题及维护、体积、权限成本。版本和命令以工程配置为准，不在规范复制易过期清单。
- 性能优化先明确场景、瓶颈与测量方式；优先消除重复 I/O、无界工作和明显的算法浪费，再考虑缓存、并行或记忆化。基准须说明环境和覆盖范围。
- 例外在变更说明中记录适用范围、原因、代价和退出条件；需要长期保持的取舍写入对应设计文档。声明例外不能替代修复已确认的数据损坏或越权问题。

交付时应能指出：行为合同、规则所属模块、关键失败证据、兼容性影响及尚未覆盖的风险。具体运行命令和证据复用条件统一查[工具索引](../../agent-tool/README.md)。
